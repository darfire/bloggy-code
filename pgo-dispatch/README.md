# pgo dispatch

A toy bytecode interpreter, compiled four ways: plain `-O2`, with PGO, and
post-link optimized with BOLT - each profile-guided one trained on either of
two workloads. Same source, same work, same checksum. What changes is
mostly how the code is laid out.

## the interpreter

`vm.c` is a `switch` over 128 ops (generated by `gen_ops.py`). Every op is 8
small steps, and after each step a check on one bit of the operand that,
when set, runs a bigger "rare case" fragment - the way real interpreter code
is fast paths interleaved with type checks, overflow checks, error
handling.

Two workloads run the same interpreter:

- **A** only uses the first half of the instruction set, **B** only the
  second half (think numeric code vs string code)
- within that half, op frequency is zipf-distributed, so a few ops are hot
  and most are warm
- the rare-case bits are set 2% of the time
- the program is built from short phrases that repeat, like real bytecode
  (loop bodies, call sequences) - a random op stream makes every dispatch a
  mispredict, which drowns out everything else

None of that is visible to the compiler. Every check looks 50/50 to it, so
it lays each rare fragment out inline, right after the check, and the hot
path has to jump over all 8 of them. With a profile, the rare fragments
move out of the way and the hot path becomes straight-line code.

## variants

- `vm_base`: `-O2`, no profile
- `vm_pgo_A`, `vm_pgo_B`: clang PGO (`-fprofile-generate`, run, `-fprofile-use`)
  trained on one workload
- `vm_pgo_AB`: PGO trained on both, profiles merged
- `vm_bolt_A`, `vm_bolt_B`: `vm_base` rewritten by BOLT with a profile of
  one workload, no recompile

## running it

```sh
./bench.sh
# debian/ubuntu, where llvm tools are only on PATH with a -18 suffix:
./bench.sh LLVM_SUFFIX=-18
```

Needs clang and llvm-profdata from the same llvm, llvm-bolt (any version -
if there's no plain `llvm-bolt`, the newest `llvm-bolt-NN` on PATH gets
used), and perf for the counters. No separate perf2bolt: it's llvm-bolt, and picks its mode
from the name it was run as - run as `perf2bolt-18` it acts as llvm-bolt
and writes a binary where the profile should be. The Makefile uses
`llvm-bolt -aggregate-only` instead, which does the same under any name.

BOLT needs a profile, and there are three ways to get one, picked with
`BOLT_PROFILE`:

- `lbr`: `perf record -j any,u`, branch records from the cpu. The intended
  way, needs hardware support (intel LBR, AMD zen 4 with linux 6.1+) and
  usually isn't available inside a VM
- `nolbr`: plain perf cycle samples. Says where the time goes but not which
  way each branch went, gets roughly half the gain
- `instr`: BOLT instruments the binary itself. Exact counts, no perf needed

Default is `lbr` if `perf record -j any,u` works on the machine, `instr`
otherwise. `make print-bolt-profile` shows which.

Two gotchas that cost me time:

- **no PIE.** A PIE build turns the `switch` into a PC-relative jump table
  that BOLT can't follow; it prints `failed to post-process indirect
  branches for run` and leaves the whole interpreter untouched. Everything
  here builds with `-fno-pie -no-pie` so all variants only differ by the
  profile.
- **link with `--emit-relocs`.** Doesn't change the code, but without it
  BOLT can't move functions around.

`ITERS` and `RUNS` (env) set the run length and repeats; time is best of
`RUNS`. `NOPS`, `NSTAGES`, `COLD_LINES` (make vars) set the code size.

## results

AMD Ryzen 7 7840HS (zen 4), clang 18, BOLT 18, bare metal, `BOLT_PROFILE=lbr`,
`ITERS=1000`:

```
| run on | binary | trained on | time    | taken branches | icache misses | speedup |
|--------|--------|------------|---------|----------------|---------------|---------|
| A      | base   | -          | 0.3302s |         651.4M |         22.9M |   1.00x |
| A      | pgo    | A          | 0.2382s |         172.8M |          5.0M |   1.39x |
| A      | pgo    | B          | 0.2840s |         646.4M |         17.7M |   1.16x |
| A      | pgo    | A+B        | 0.2472s |         181.5M |         10.3M |   1.34x |
| A      | bolt   | A          | 0.2474s |         168.9M |          7.3M |   1.33x |
| A      | bolt   | B          | 0.2713s |         585.6M |         18.6M |   1.22x |
| B      | base   | -          | 0.3057s |         643.4M |         21.6M |   1.00x |
| B      | pgo    | A          | 0.2907s |         643.2M |         18.4M |   1.05x |
| B      | pgo    | B          | 0.2388s |         174.0M |          5.2M |   1.28x |
| B      | pgo    | A+B        | 0.2483s |         173.1M |         11.8M |   1.23x |
| B      | bolt   | A          | 0.2817s |         578.3M |         17.4M |   1.09x |
| B      | bolt   | B          | 0.2415s |         171.2M |          5.8M |   1.27x |
```

Instruction counts barely move (5.76G for base on A, 5.34G for PGO, 5.68G
for BOLT, measured in the VM - mostly the jumps that are no longer needed), nowhere near enough
to explain a 1.3x; the gain is front end. Taken branches drop ~4x when the
profile matches - from ~10 per op (jumping over every rare fragment) to
~2.6 - and icache misses drop ~4x with them.

With a profile from real branch records, BOLT gets within a few percent of
PGO, without recompiling anything.

Trained on the wrong workload, both get much less, and not consistently -
1.16x/1.22x on A but only 1.05x/1.09x on B. The profile says the other half
of the instruction set is cold, so none of the layout work goes where it's
needed. Training on both gets most of the gain on both, but the icache
misses show the cost - twice the hot code, sharing the same 32KB.

Same chip inside a VM (microsandbox), where there are no branch records:
`BOLT_PROFILE=instr` gets about the same as `lbr` (1.29x/1.21x),
`BOLT_PROFILE=nolbr` only ~1.13x - plain cycle samples say where the time
goes, not which way each branch went.

# icache pipeline staging

Third one in this series, different cache than the other two
([`../matrix-cache-aliasing`](../matrix-cache-aliasing),
[`../matmul-cache-aliasing`](../matmul-cache-aliasing)) - this one's about
the instruction cache, not data.

Two ways to run the same N operations over a batch of items, same result
either way:

- **fused**: for each item, run all N ops back to back, then move to the
  next item
- **staged**: for each op, run it over every item, then move to the next op

This is a real architectural choice, not a made-up one - it's "process one
entity through its whole pipeline" vs "run one pass over everything," which
shows up in game engines (ECS), image pipelines, interpreters, anywhere you
process a batch through several stages.

## why fused is slower

If the combined code for all N ops doesn't fit in L1i (32KB on a typical
8-way setup), fused never gets to reuse any of it: every item walks through
all N functions again, and by the time it's back to op 0 for the next item,
op 0's code has long been evicted to make room for the other 95. Staged
only ever needs one op's code hot at a time, so each function's code gets
fetched once (when a stage starts) and then just... stays, for however many
items are in the batch.

Important detail: both versions call the ops directly (not through function
pointers), on purpose. An earlier version of this used an array of function
pointers and the slowdown was mostly branch misprediction on the indirect
call, not icache pressure. Direct calls to 96 distinct generated functions
remove that confound - branch-misses end up nearly identical between the
two versions, icache-load-misses doesn't.

## running it

```sh
make all
./bench.sh
```

`ops.c`/`ops.h` are generated by `gen_ops.py` (96 distinct noinline
functions by default - distinct bodies matter, otherwise the compiler just
folds identical functions back together). `make all` regenerates and builds
both `pipeline_fused` and `pipeline_staged`.

single run, to sanity check both give the same checksum:

```sh
./pipeline_fused 10000
./pipeline_staged 10000
```

## results

```
| nitems  | mode         | time     | icache misses | speedup |
|---------|--------------|----------|---------------|---------|
|    2000 | fused        |   0.0104s |          4894 |   1.00x |
|    2000 | staged       |   0.0025s |          1493 |   4.16x |
|   20000 | fused        |   0.0589s |         26992 |   1.00x |
|   20000 | staged       |   0.0179s |          1372 |   3.29x |
|  200000 | fused        |   0.5617s |        202202 |   1.00x |
|  200000 | staged       |   0.1840s |          4705 |   3.05x |
```

the icache miss *rate* (misses/loads) actually looks backwards if you check
it - fused's rate is lower because it does way more total icache fetch
traffic overall. the raw counts are what tell the real story: staged's miss
count barely grows with nitems (it only pays for each op's code once per
stage), fused's grows roughly linearly with nitems (every item re-triggers
misses across all 96 functions).
